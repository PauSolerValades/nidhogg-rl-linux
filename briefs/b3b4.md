# Worker B3/B4 — validate the two phase candidates, then write-test them

**Goal (falsifiable):** one of the two candidates below is the round phase — it steps exactly once
per round boundary *and* writing it changes the round's behaviour. Success = a field whose write
ends/resumes a round, twice, both directions. A clean negative ("the value flips but nothing
behaves differently") is a full result.

## Where they came from

A global 2.7 GB boundary diff was saturated by draw state (763 survivors, 702 = HUD text alpha).
Restricting the diff to **live instance state** (via the engine's instance list, head at
`type+0xa0`) and then requiring *constant within a phase across 4 snapshots* AND *the same flip in
two consecutive cycles* left exactly two slots:

| candidate | kind | live | round over | owner |
|---|---|---|---|---|
| `node+0x08` | instance node header flags | `0x1` | `0x101` | a **singleton node** (`prev=0, next=0`), type `0x16ea800`, id `0x19511`, record `xy=(0,0)` — a controller, not a physical object |
| `rec+0xfc` | instance record field | `0` | `117` | belongs to some other instance |

Reproduce with `python3 scripts/phase_filter.py 0` (needs a live match; ~4 min; expect ~2 hits).

**Addresses are per-process and node memory is recycled: re-derive them on your own instance,
never hard-code the numbers above.**

## Step 1 — B3: do they flip exactly once per boundary?

Use `n.watch(pid, [...])` + `n.watched(pid)`: up to 16 u32s sampled on the **same per-tick seam as
the state file**, so you get a 60 Hz time series of the candidates.

1. Track the game tick (`n.track(pid, tick=…)`) so watch samples line up with ticks.
2. Record 4–5 boundaries (forfeit → winner screen → continue). **Ground truth is the winner
   screen**, detected from the frame change (a 100k+ pixel jump; 3/3 reliable) — *not*
   `on_ready_screen`, which is too strict and made an earlier run unable to assert anything.
3. PASS: each candidate flips exactly once per boundary, and does not flip while the round is live
   (a 20 s quiet window with no key presses).

## Step 2 — B4: does writing it change behaviour?

This is the decisive one. A value that matches the screen can still drive nothing (the ORANGE
score taught us exactly that).

* **At the winner screen**, write the *live* value (`0x1` for the node flag) → the round should
  resume: the GO/play state returns. Accept only if it visibly happens, twice.
* **During a live round**, write the *over* value (`0x101`) → the round should end (winner/GO).
  Accept only if it visibly happens, twice.
* **Restore** the original value after each attempt; `n.ping` after every write; **integers only**
  (a float write killed a process once); one candidate at a time.
* If the game dies, that is a reportable outcome — note which candidate/value and stop.

## Rules

* Your farm and display are in the environment; use `n.start_ids([0])` / `n.stop_id(0)` only.
* **Never** `pkill -x Nidhogg.exe` (shared box, other lanes).
* Never press `d`/`a` repeatedly in a match: walking into the goal ends the round you are measuring.
* The forfeit recipe, exactly (each detail cost a session):
  `Escape` → 1.6 s → `Down`(hold 0.12) → 0.65 s → `Down`(hold 0.12) → `Return` → 1.3 s →
  `Right` → `Return` (the dialog cursor starts on **NO**) → 2.5 s = winner screen → `Return` = continue.
  The dialog **repaints nothing** when `Right` moves the cursor, so do not use a pixel diff to
  check that press.
* Record every claim with `tools/claim.py` (stable `cmd`, no pids; falsifier exits **2** for
  "could not run", **1** only for "claim false").
